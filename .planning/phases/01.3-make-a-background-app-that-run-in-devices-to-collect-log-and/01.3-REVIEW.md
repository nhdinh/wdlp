# Phase 01.3: Code Review Report

**Reviewed:** 2026-08-23T05:00:00Z

**Files Reviewed:** 13

## Summary

The development log service has two ship-blocking boundary defects: Windows dispatcher startup failure is reported to the operating system as success, and path authorization is separated from the file open by a race that can invalidate the authorization decision. Error classification and SCM startup-state handling also have robustness defects. The portable test suite and Clippy pass, but neither exercises the Windows process exit contract or a filesystem replacement race.

## Narrative Findings (AI reviewer)

## Critical Issues

### CR-01: Windows dispatcher failure exits with success status

**File:** `crates/dlp-log-debug-service/src/main.rs:5-8`
**Issue:** The Windows `main` function returns `()`. When `run_scm_service()` fails, it prints `service_dispatcher_failed` and then returns normally, so the process exit code is zero. Service startup invoked outside the SCM, dispatcher registration failures, and other immediate dispatcher errors are therefore indistinguishable from successful termination to deployment scripts and supervisors. This contradicts the stable nonzero lifecycle-failure contract and can leave automation believing the debugger is running when it never started.
**Fix:** Return `std::process::ExitCode` on Windows and map dispatcher failure to `ExitCode::FAILURE` (or terminate with a documented stable nonzero code); return `SUCCESS` only after a successful dispatcher lifetime.

### CR-02: Authorization and file open are vulnerable to a filesystem replacement race

**File:** `crates/dlp-log-debug-service/src/paths.rs:54-59`
**Issue:** `authorize_requested_file` canonicalizes and validates a pathname, returns that pathname, and `read_bounded_tail` opens it later in `tail.rs:20`. Between validation and open, an attacker able to mutate entries in an allowed directory can replace the validated file or an ancestor with a symlink/junction/reparse point. The subsequent open can then resolve to a file outside the allowed folder, bypassing the direct-child authorization boundary and exposing arbitrary readable file content. Canonicalization is not an atomic authorization primitive.
**Fix:** Open the file first with platform protections that reject reparse-point traversal, validate the opened handle's final canonical path and file type, and read from that same handle. On Windows, obtain the final path from the handle and use an open mode that prevents following reparse points where appropriate; do not reopen by pathname after validation.

## Warnings

### WR-01: Every query-deserialization failure is mislabeled as an invalid tail

**File:** `crates/dlp-log-debug-service/src/http.rs:139`
**Issue:** Any `QueryRejection` is converted to `HttpError::InvalidTail`, including duplicate or otherwise malformed `path` fields. Clients receive a misleading stable code and cannot distinguish a malformed path/query from a bad tail value. This also makes the advertised fixed error contract dependent on Serde rejection details rather than the offending field.
**Fix:** Deserialize into a raw query representation that validates `path` and `tail` independently, or inspect/map the rejection so path/query-shape failures produce `invalid_path` while only tail parse/range failures produce `invalid_tail`.

### WR-02: Handler-registration failure never reports a stopped service status

**File:** `crates/dlp-log-debug-service/src/service.rs:75-79`
**Issue:** If control-handler registration fails, the service callback logs `runtime_failed` and returns without reporting `Stopped` or a service-specific exit code. This bypasses `stop_with_error` and breaks the stated stable lifecycle error contract; SCM observers instead see an implementation-dependent abrupt service-main return.
**Fix:** Restructure startup so registration errors propagate to a boundary that can produce a deterministic process failure, and where a status handle exists route all later startup errors through one stopped-status path. Document the unavoidable pre-handle dispatcher/registration error separately from service-specific status codes.
