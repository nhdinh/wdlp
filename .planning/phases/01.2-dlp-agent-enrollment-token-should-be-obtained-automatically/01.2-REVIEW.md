# Phase 01.2: Code Review Report

**Reviewed:** 2026-08-28T06:38:25Z
**Depth:** deep
**Files Reviewed:** 12
**Status:** issues_found

## Summary

The automatic-enrollment path contains seven ship-blocking correctness/security defects. The most serious are a recovery authorization bypass in the normal path, fail-open credential deletion, stale-cache evidence that can report a broken replacement as successful, trust-all TLS probes that publish misleading evidence, and plaintext token persistence without an enforced ACL. Three additional test/secret-lifecycle weaknesses reduce confidence in the claimed failure and redaction coverage.

## Critical Issues

### CR-01: DC01 evidence probes disable certificate validation

**Classification:** BLOCKER

**File:** `scripts/lab/Invoke-Dc01Server.ps1:588-607` (also `:640-650`)

**Issue:** Both `ReadinessConcurrency` and `Invoke-Dc01Tracer` install `TrustAllCertsPolicy`, whose callback unconditionally returns `true`. The tracer then records successful readiness evidence even though server identity, hostname, and CA trust were never authenticated. This directly contradicts the phase summary's explicit-CA claim and permits a TLS-intercepted endpoint to satisfy the evidence workflow.

**Fix:** Remove `ICertificatePolicy` overrides. Probe `LAB-DC01.lab.local` with the explicit Phase 1 CA (for example, `curl.exe --cacert <root>`) and keep hostname validation enabled. Make evidence publication conditional on those authenticated probes, and add a source gate over both executable runners, not only documentation.

### CR-02: Normal enrollment silently authorizes server-side credential recovery

**Classification:** BLOCKER

**File:** `scripts/lab/Invoke-Client01Runtime.ps1:1494-1507`

**Issue:** Every TrustedProvisioning request that does not reuse a local file passes `-RecoverCredential`, even when `-ForceReenrollment` was not supplied. That flag reaches `PgAuthorityRepository::provision`, where recovery revokes the current active serial and clears `active_serial`. Therefore a missing/empty local `device.dpapi` makes an ordinary `ServiceInstall` mutate server credential authority, bypassing the phase's explicit `-ForceReenrollment -Apply` replacement boundary.

**Fix:** Pass `-RecoverCredential` only when `$ForceReenrollment` is true. Initial provisioning should use the non-recovery request. If server authority already exists while local state is missing, fail with a stable instruction to rerun explicitly with `-ForceReenrollment -Apply`; add a regression test that proves ordinary ServiceInstall cannot revoke an existing serial.

### CR-03: Force reset reports completion even when credential deletion fails

**Classification:** BLOCKER

**File:** `scripts/lab/Invoke-Client01Runtime.ps1:351-369`

**Issue:** The SYSTEM task runs `del ... & echo complete`, so the completion marker is written regardless of `del` success, and the caller never verifies that `device.dpapi*` is absent. If deletion fails, trusted recovery has already revoked the server serial, but service startup reuses the still-present local credential. Because the service can run with a rejected credential and the preserved cache is accepted as Active, the force scenario can report success while the endpoint is no longer authorized.

**Fix:** Make the task write success only after a successful delete and an explicit absence check, return a failure marker/exit code otherwise, and verify the credential glob is empty after the task. The live replacement test must also prove the certificate serial changed and the predecessor is rejected, not merely that the service is Running.

### CR-04: Re-fetching the current signed policy is treated as a configuration failure

**Classification:** BLOCKER

**File:** `crates/dlp-windows-service/src/service.rs:313-323`

**Issue:** `poll_and_activate` sends every fetched bundle to `stage_verify_activate` and maps all cache errors to `ConfigurationFetchFailed`. The cache rejects `version <= current_version`, while the server normally returns the already-selected current version. After the first activation, every restart/reuse poll of the unchanged valid bundle is therefore logged and reported as `ConfigurationRejected`, and `last_contact` never advances. The defined `ActivationOutcome::Unchanged` path is never used.

**Fix:** Make equal-version, equal-digest, valid signed content idempotently return `ActivationOutcome::Unchanged`; reject lower versions and same-version/different-content conflicts. Treat `Unchanged` as successful contact in `poll_and_activate`, and add a service restart test against an already-populated cache.

### CR-05: Active-policy acceptance can pass entirely from stale cache state

**Classification:** BLOCKER

**File:** `scripts/lab/Invoke-Client01Runtime.ps1:1402-1433`; `tests/windows/Invoke-AgentServiceSmoke.ps1:166-184,284-305`

**Issue:** `Wait-Client01ActivePolicy` accepts any pre-existing pointer with a nonzero version. It does not establish that the current service start authenticated, fetched, or activated a policy. `InitialEnrollmentCredential` does not clear or reject pre-existing credential/cache state, and replacement intentionally preserves cache. Thus the initial test can skip provisioning, and the replacement test can pass using the old pointer even when the new credential is absent/revoked or every poll fails (including CR-03/CR-04).

**Fix:** Isolate the initial scenario with a verified no-credential/no-pointer precondition. For reuse/replacement, capture a baseline and require a post-start authenticated-poll signal (or server-observed health/contact bound to the new serial), plus explicit new-serial activation and predecessor revocation. Do not use pointer existence alone as proof of this run's end-to-end success.

### CR-06: The one-time enrollment token is written to a plaintext file without a protected ACL

**Classification:** BLOCKER

**File:** `scripts/lab/Invoke-Client01Runtime.ps1:1237-1268`

**Issue:** The token is embedded in `agent.env` and written with `WriteAllLines`, but this path never creates or verifies a restrictive ACL. The surrounding installation code creates `C:\dlp\agent` with inherited permissions. Security therefore depends on ambient filesystem ACLs, and a local user who can read the file during startup can steal the token and race the endpoint's unauthenticated bootstrap enrollment request.

**Fix:** Before writing any token, protect the directory/file ACL and grant only SYSTEM, Administrators, and the required service identity; fail closed if ACL verification fails. Prefer atomic creation with the final protected descriptor. Add an ACL assertion to the live smoke test and verify an ordinary user cannot read `agent.env` while enrollment is pending.

### CR-07: The DC01 runner drops the supported signing key identifier override

**Classification:** BLOCKER

**File:** `scripts/lab/Invoke-Dc01Server.ps1:405-430`

**Issue:** Server and service composition now support `DLP_CONFIGURATION_KEY_ID`, and the endpoint runner persists it, but `Invoke-Dc01Server.ps1` omits it from the server environment. With any supported non-default value, LAB-DC01 signs under its compiled default while LAB-CLIENT01 verifies the configured override, so first policy activation fails. Readiness does not compare this configuration value, so an already-running mismatched server can still be considered ready.

**Fix:** Propagate `DLP_CONFIGURATION_KEY_ID` into the DC01 environment with the same default/validation used by both Rust components. Include a non-secret key-ID equality check in readiness and add an integration case using a non-default identifier.

## Warnings

### WR-01: The service retains the plaintext token for its full process lifetime

**Classification:** WARNING

**File:** `crates/dlp-windows-service/src/service.rs:121-190`

**Issue:** `ensure_credential` clones `config.enrollment_token`; the coordinator zeroizes only that clone. The original remains inside `ServiceContext.config` after startup and survives for the service loop's lifetime, even after the file and registry copies are removed.

**Fix:** Accept mutable config, `take()` the token before enrollment, zeroize that owned value on all paths, and construct `ServiceContext` with `enrollment_token: None`. Remove the process environment value at the safe single-threaded startup boundary if supported.

### WR-02: Failure-path tests model cleanup instead of invoking the implementation

**Classification:** WARNING

**File:** `tests/windows/Invoke-AgentServiceSmoke.ps1:338-359`

**Issue:** `InstallStartFailureCleanup`, `CleanupFailure`, and `FreshTokenRetry` operate on `Invoke-TokenCleanupModel` or regex-presence checks. They never fault-inject the actual `Remove-Client01EnrollmentToken`/install wiring, so they can remain green when real cleanup is skipped, only one location is modified, or task execution fails.

**Fix:** Extract cleanup behind a testable command adapter and run it against isolated file/registry fixtures with injected failures for each location. Keep static checks only as supplemental contract tests.

### WR-03: Secret-content gates miss normal line-wrapped PEM blocks

**Classification:** WARNING

**File:** `tests/lab/EnrollmentTokenOrchestration.Tests.ps1:70-82`

**Issue:** The PEM regexes require one contiguous base64 run between BEGIN/END markers. Conventional PEM bodies are wrapped across multiple lines, so a complete private key or certificate can be added to operator documentation without failing this gate.

**Fix:** Parse all BEGIN/END PEM blocks, normalize whitespace inside the body, and reject any non-placeholder decoded content. Add fixtures with 64-character wrapped certificate and private-key bodies.
