## Phase Goal

**As an** authorized Windows user, **I want to** have protected-drive operations evaluated against assigned policy with clear feedback, **so that** sensitive files remain inside the organization’s DLP boundary.

<objective>
Ship the native per-user companion and prove the complete Phase 2 policy/feedback boundary on real Windows sessions, including restart, cross-user isolation, and revoked-device rejection.

Purpose: The service-side contract must end in an actual privacy-safe Windows notification and survive the session/machine conditions users experience.
Output: Companion executable, Windows notification adapter/registration, session lifecycle integration, and a redacted Phase 2 Windows smoke/evidence matrix.
</objective>

## Scope Cohesion and Safe Execution Boundaries

This plan intentionally keeps its eleven-file surface together because the native companion is one security boundary whose notification adapter, authenticated process lifecycle, service orchestration, integration tests, and machine-bound evidence share protocol and lifecycle contracts. Splitting the lab/evidence task into another plan would either duplicate ownership of `companion_grants.rs` and the companion/service contracts or permit acceptance against a different build than the one exercised in the lab. Execution remains bounded: Task 1 owns the notification adapter and companion tracer (five files), Task 2 owns session/service lifecycle expansion (four files), and Task 3 owns only the smoke script, evidence, and validation sign-off (four files). Tasks execute sequentially; each source-producing task completes its focused fail-fast tests and commit before the next begins, and Task 3 cannot start until its explicit lab precondition and the full workspace gate are satisfied.
