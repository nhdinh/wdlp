## User Constraints (from CONTEXT.md)

### Locked Decisions

### Process Ownership and Lifecycle
- **D-01:** Implement the debugger as a separate Windows service, not inside `DlpWindowsService` or a per-user companion.
- **D-02:** The service is development-only and remains outside the DLP ecosystem. It must not participate in enrollment, management-server registration, policy, health reporting, or production deployment.
- **D-03:** Developers install, start, stop, and remove it manually with standard Windows commands. No repository-managed installer or automatic lab provisioning is required.
- **D-04:** Failure or absence of the debugging service has no effect on any DLP component.
- **D-05:** Keep the implementation in a dedicated Cargo workspace crate and exclude it from production packaging.

### HTTP Access Boundary
- **D-06:** Listen on all network interfaces to support remote access from other lab machines.
- **D-07:** Authorize remote clients with a configurable source-IP allowlist; identity-based authentication is not required for this development tool.
- **D-08:** Store trusted client IPs in a local configuration file.
- **D-09:** If the configuration is missing, invalid, or has no trusted clients, continue in localhost-only mode and reject remote requests.

### File Authorization and Reading
- **D-10:** The client requests a specific absolute log-file path. The service does not discover or aggregate logs automatically.
- **D-11:** Permit a request only when the resolved file is a direct child of a folder allowlisted in the local configuration. Nested descendants are not implicitly authorized.
- **D-12:** Read the source file and return its content directly. Do not cache, copy, archive, or otherwise retain requested log data.
- **D-13:** Return a bounded tail snapshot for large or actively written files. The maximum response size is configurable and remains a hard safety cap.

### HTTP API Contract
- **D-14:** Use `GET /logs?path=<absolute-path>&tail=<line-count>`.
- **D-15:** On success, return only plain log text. Do not wrap it in JSON or attach diagnostic metadata headers.
- **D-16:** If the byte cap prevents satisfying the requested line count, return the newest complete lines that fit without adding a truncation marker.
- **D-17:** Invalid and unsuccessful requests use standard HTTP statuses with short plain-text error codes, such as `invalid_tail`, `untrusted_client`, or `file_not_found`. Do not expose filesystem or operating-system error details.

### the agent's Discretion
- Configuration file format and default location.
- Default HTTP port and the configurable maximum response size.
- Exact HTTP status mapping and short error-code vocabulary, provided it follows D-17.
- Crate and Windows service names.

## Summary

Implement a new, independent `dlp-log-debug-service` Cargo workspace crate and Windows SCM service. It must own its own runtime, listener, local JSON configuration, and shutdown path; it must not reference `dlp-agent-core`, DLP enrollment/configuration code, or the `DlpWindowsService` process. This honors the explicit separation and non-production boundary. [VERIFIED: `.planning/phases/01.3-make-a-background-app-that-run-in-devices-to-collect-log-and/01.3-CONTEXT.md:17-21`]

The service should bind the configured TCP port on all interfaces, then authorize every request from the TCP peer address—not `X-Forwarded-For` or another request header. Remote traffic must pass both the Windows Firewall rule scoped to the configured port/program and the application source-IP allowlist. Missing, malformed, or empty-trust configuration must retain a running loopback-only diagnostic mode but expose no authorized files because no folder allowlist is valid. Microsoft documents firewall rules scoped by `Program`, `LocalPort`, and `RemoteAddress`; that host rule is a separate, necessary network boundary. [CITED: https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule?view=windowsserver2025-ps]

For an authorized request, canonicalize the existing requested file and each configured folder, require exact equality between the canonical file parent and a canonical configured folder, then take one bounded end-of-file snapshot. Discard a leading partial line after a capped seek and a trailing unterminated line; return only the newest requested number of complete lines that fit. Rust documents that files can change concurrently, so this is intentionally a snapshot rather than a consistency guarantee. [CITED: https://doc.rust-lang.org/stable/std/fs/struct.File.html]

**Primary recommendation:** Build a `dlp-log-debug-service` crate using the already locked Axum, Tokio, `windows-service`, Serde, and `serde_json` packages; put authorization and tail-reading in pure, unit-testable modules and keep SCM glue thin.

### Pattern 1: Separate SCM Adapter and Application Core

**What:** `main.rs` enters `service_dispatcher`; `service.rs` registers `Stop` and `Shutdown`, reports pending/running/stopped state, and owns a cancellation signal. The router, authorization, config validation, and tail algorithm remain normal safe Rust functions. [CITED: https://docs.rs/windows-service/0.8.1/windows_service/service_dispatcher/fn.start.html]

**When to use:** Always for this phase—the existing DLP service shows the local SCM convention, but it must be copied as a pattern, not imported or extended. The current service’s primitive log path is exactly `r"C:\dlp\agent\logs\dlp-windows-service.log"`. [VERIFIED: `crates/dlp-windows-service/src/service.rs:19-44`]

**Example:**


### Pattern 2: Fail-Closed Config Mode

**What:** Decode JSON to a typed structure and run semantic checks before listener startup: numeric port, positive byte cap, absolute folder paths, canonicalizable folders, and syntactically valid IP addresses. If any check fails—or trusted-client list is empty—create a `LocalhostOnly` access policy and an empty folder set; do not terminate merely for configuration invalidity. [VERIFIED: `.planning/phases/01.3-make-a-background-app-that-run-in-devices-to-collect-log-and/01.3-CONTEXT.md:23-33`]

**Recommended discretionary defaults:** JSON at `C:\ProgramData\DlpLogDebugService\config.json`, Windows service name `DlpLogDebugService`, TCP port `9191`, and `262144` maximum response bytes. These are implementation recommendations, not locked product values. [ASSUMED]

**Required local hardening:** Documentation must require an Administrator-created directory/file ACL permitting only `SYSTEM` and Administrators to alter the config, plus a manually created inbound firewall rule restricted to that executable, port, and configured remote IPs. Do not let the service create either rule automatically. [ASSUMED; CITED: https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule?view=windowsserver2025-ps]

### Pattern 3: Canonical Direct-Child Authorization Before Read

**What:** Validate an absolute request path; canonicalize the existing target; reject directories; derive its canonical parent; authorize only if that parent is exactly one canonical configured folder. Canonicalization resolves symbolic links and normalization before the parent comparison. [CITED: https://doc.rust-lang.org/std/fs/fn.canonicalize.html]

**When to use:** Before opening every requested file. Never authorize with string-prefix comparison or permit a configured folder’s descendants implicitly.

### Pattern 4: Bounded Complete-Line Tail

**What:** Obtain metadata length, seek to `length.saturating_sub(max_response_bytes)`, read at most the cap, drop the prefix fragment when the seek began after byte zero, and retain only newline-terminated segments. Select the newest `tail` segments within the already bounded buffer. A read shortened by concurrent file truncation is still a valid best-effort snapshot. [CITED: https://doc.rust-lang.org/std/io/index.html; CITED: https://doc.rust-lang.org/stable/std/fs/struct.File.html]

**Example:**

```rust
// Source: https://docs.rs/axum/0.8.9/axum/fn.serve.html
let listener = tokio::net::TcpListener::bind(listen_address).await?;
axum::serve(listener, app).await?;
```

### Anti-Patterns to Avoid

- **Integrating this endpoint into `DlpWindowsService`:** breaches the explicit independent-process and zero-impact boundary. [VERIFIED: `.planning/phases/01.3-make-a-background-app-that-run-in-devices-to-collect-log-and/01.3-CONTEXT.md:17-21`]

## Common Pitfalls

### Pitfall 1: A Valid Local Config Accidentally Enables Remote File Access

**What goes wrong:** A permissive firewall rule or writable config allows an untrusted client to reach a service running as a privileged account. [ASSUMED]  
**Why it happens:** Binding all interfaces is locked, while a source-IP allowlist alone does not stop hostile traffic from reaching the process. [VERIFIED: `.planning/phases/01.3-make-a-background-app-that-run-in-devices-to-collect-log-and/01.3-CONTEXT.md:23-27`]  
**How to avoid:** Require a manually scoped inbound firewall rule and protected config ACL; test untrusted remote IP rejection in the handler and at the firewall boundary. [CITED: https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule?view=windowsserver2025-ps]  
**Warning signs:** A wildcard/`Any` RemoteAddress rule, config directory writable by ordinary users, or request paths in the debugger’s own logs. [ASSUMED]

### Pitfall 2: Traversal or Link Escape

**What goes wrong:** A syntactically allowed path resolves outside the intended folder. [ASSUMED]  
**Why it happens:** Normalizing a string or checking `starts_with` is not equivalent to resolving the file-system object. [ASSUMED]  
**How to avoid:** Canonicalize target and allowed folders; compare `target.parent()` by exact path equality; reject folders and nested descendants. [CITED: https://doc.rust-lang.org/std/fs/fn.canonicalize.html]  
**Warning signs:** Tests pass only normal paths and omit `..`, symlink/junction, sibling-prefix, and nested-file cases. [ASSUMED]

### Pitfall 2a: Check/Use Race on a Mutable Path

**What goes wrong:** A locally writable log directory can change the resolved object after canonical authorization but before the service opens/reads it. [ASSUMED]  
**Why it happens:** `canonicalize` and `File::open` are separate filesystem operations; Rust documents that files can be concurrently modified. [CITED: https://doc.rust-lang.org/stable/std/fs/struct.File.html]  
**How to avoid:** Document that configured directories must not be writable by untrusted principals; authorize the canonical target and open that canonical path immediately. Treat stronger handle-based final-path verification as a follow-up only if the lab threat model includes a hostile local writer. [ASSUMED]  
**Warning signs:** A test can replace an allowed file with a link between authorization and read. [ASSUMED]

### Pitfall 3: Partial or Oversized Output

**What goes wrong:** The service returns a partial line, loads an entire large file, or appends a truncation marker that changes the source log text. [ASSUMED]  
**Why it happens:** A naïve `read_to_string` ignores both concurrent writers and the response-size boundary. Rust documents concurrent file modification as possible. [CITED: https://doc.rust-lang.org/stable/std/fs/struct.File.html]  
**How to avoid:** Seek/read a capped suffix, discard incomplete edge fragments, then select newest complete lines without modifying them. [CITED: https://doc.rust-lang.org/std/io/index.html]  
**Warning signs:** Allocation proportional to full source file size, a `truncated` marker, or a last returned line lacking its terminator. [ASSUMED]

### Pitfall 4: SCM Hangs During Stop

**What goes wrong:** The service reports `Running` but cannot stop because its HTTP future has no cancellation path. [ASSUMED]  
**Why it happens:** `service_dispatcher::start` blocks until the service stops, and SCM control handling is separate from the async listener. [CITED: https://docs.rs/windows-service/0.8.1/windows_service/service_dispatcher/fn.start.html]  
**How to avoid:** Send a cancellation signal from `Stop`/`Shutdown`, use graceful shutdown around Axum serving, await the server task before reporting `Stopped`. [ASSUMED]  
**Warning signs:** `Stop-Service` times out or the service remains `StopPending`. [ASSUMED]

```rust
// Source: https://doc.rust-lang.org/std/io/index.html
use std::io::{Read, Seek, SeekFrom};

fn read_suffix(file: &mut std::fs::File, offset: u64) -> std::io::Result<Vec<u8>> {
    file.seek(SeekFrom::Start(offset))?;
    let mut bytes = Vec::new();
    file.read_to_end(&mut bytes)?;
    Ok(bytes)
}
```

The production helper must preallocate/read no more than the configured cap; this short official pattern demonstrates `Seek` plus `Read`, not the required cap enforcement. [CITED: https://doc.rust-lang.org/std/io/index.html]

## Open Questions

1. **What should happen for a requested file whose bounded tail is not valid UTF-8?**
   - What we know: Success must be plain log text only, while the existing early service logger writes UTF-8 strings. [VERIFIED: `crates/dlp-windows-service/src/service.rs:19-44`]
   - What's unclear: The phase allows explicit arbitrary log-file paths, whose encoding is not constrained.
   - Recommendation: Treat non-UTF-8 as `read_failed` with no detail for this phase; do not silently transcode or return binary. [ASSUMED]

2. **Must the manual firewall rule be part of the phase’s operator documentation and Windows VM verification?**
   - What we know: Remote all-interface access is locked, and Microsoft supports program/port/remote-address firewall scoping. [VERIFIED: `.planning/phases/01.3-make-a-background-app-that-run-in-devices-to-collect-log-and/01.3-CONTEXT.md:23-27`; CITED: https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule?view=windowsserver2025-ps]
   - What's unclear: D-03 rules out a managed installer, not a manual documented rule.
   - Recommendation: Make the rule a required manual setup/verification step, but do not automate it in repository provisioning. [ASSUMED]

3. **Does the development lab threat model include hostile local writers to an allowlisted log directory?**
   - What we know: The required canonical direct-child check prevents ordinary traversal/link resolution before the read, but concurrent filesystem changes remain possible. [CITED: https://doc.rust-lang.org/stable/std/fs/struct.File.html]
   - What's unclear: Whether endpoint log folders are writable by a non-administrator considered hostile in this development-only service’s scope.
   - Recommendation: Plan protected config plus developer-controlled log folders now; require a separate security decision before adding Windows handle-level final-path enforcement. [ASSUMED]
