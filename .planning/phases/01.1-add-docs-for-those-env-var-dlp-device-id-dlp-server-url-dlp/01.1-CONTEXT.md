# Phase 01.1: Endpoint Service Environment-Variable Documentation - Context

**Gathered:** 2026-08-28
**Status:** Ready for replanning

<domain>
## Phase Boundary

Document every runtime environment variable consumed by the DLP Windows endpoint service. Give operators complete instructions for collecting or creating, validating, persisting, deploying, and troubleshooting every required and optional endpoint-service variable. Keep server, provisioning, AD, and orchestration-only variables outside this guide except for links to their canonical documentation. This phase changes documentation only; it does not change runtime behavior.

</domain>

<decisions>
## Implementation Decisions

### Coverage Boundary
- **D-01:** Give every required and optional endpoint-service variable equal procedural depth, including purpose, collection or creation, validation, persistence, and troubleshooting.
- **D-02:** For conditional variables such as `DLP_AGENT_ENROLLMENT_TOKEN`, document trusted provisioning as the normal path and manual or offline configuration as the alternative.
- **D-03:** Do not duplicate server, provisioning, AD, or orchestration-only variable documentation. Link to the appropriate canonical guide instead.
- **D-04:** Build the authoritative endpoint-variable inventory by reconciling `dlp-windows-service` source consumption with `scripts/lab/Invoke-Client01Runtime.ps1` persistence and inputs. Document any mismatch explicitly.

### Operator Journey
- **D-05:** Put a complete end-to-end setup workflow before the detailed per-variable reference catalog.
- **D-06:** Target the Phase 1 Hyper-V lab operator and use the concrete `hungdinh-lt` → `LAB-CLIENT01` → `LAB-DC01` topology. Add generic or production notes only where behavior differs.
- **D-07:** Lead with `scripts/lab/Initialize-DlpEnvironment.ps1`, explain each prompt and the source of its value, and retain manual PowerShell setup as the fallback.
- **D-08:** Structure the workflow as collect → validate → persist → deploy → verify, with a clear expected result after every stage.
- **D-09:** Keep `.planning/docs/ENV-VARS.md` as the canonical detailed reference. Other runbooks may retain concise reminders but must link back to it rather than duplicate acquisition instructions.

### Examples and Secret Handling
- **D-10:** Use real Phase 1 lab machine names, ports, paths, key IDs, intervals, and drive letters in committed examples. Use synthetic material for certificates, keys, tokens, passwords, and other secrets.
- **D-11:** Secret placeholders must be visibly non-runnable, such as `<FROM-RUNTIME-PROVIDER>` or `*** REPLACE ME ***`, so accidental copy-paste fails immediately.
- **D-12:** Distinguish cryptographic secrets, sensitive identifiers, and public trust material. State appropriate storage and sharing rules for each rather than labeling every required value a secret.
- **D-13:** Explain all persistence layers: transient PowerShell input, generated `agent.env`, and the Windows service registry `Environment` value. Identify which tool writes each layer and warn operators not to edit generated copies independently.
- **D-14:** `DLP_ROOT_CA_PEM` documentation must preserve both supported forms: inline PEM content and an absolute PEM file path.

### Validation and Troubleshooting
- **D-15:** Provide safe, copy-paste PowerShell checks for every variable. Checks must verify presence, format, path access, certificate or key shape, and service visibility without printing sensitive values.
- **D-16:** Add a stable error-to-fix matrix mapping errors such as `runtime_secrets_missing`, `service_config_missing`, and `service_config_invalid` to likely variables, redacted checks, and corrective actions.
- **D-17:** Required end-to-end verification covers generated configuration, registry persistence, Windows service startup, and passing redacted health or diagnostics. Successful enrollment and first configuration polling are not required by this documentation phase.
- **D-18:** If troubleshooting exposes sensitive material, instruct the operator to stop copying output, safely remove exposed artifacts, rotate the affected material, and resume only with redacted diagnostics.

### Agent Discretion
- Exact headings, table column names, prose length, and command formatting may follow the established documentation style as long as the decisions above remain explicit and discoverable.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `.planning/docs/ENV-VARS.md`: Already contains the endpoint variable inventory, four acquisition sections, persistence explanation, PowerShell template, and related-document links; extend and reorganize it rather than creating a competing guide.
- `scripts/lab/Initialize-DlpEnvironment.ps1`: Existing guided prompt flow should anchor the setup-first operator journey.
- `scripts/lab/Invoke-Client01Runtime.ps1`: Existing validation and persistence behavior should supply copy-paste checks, expected results, and stable error names.
- `.planning/docs/HYPERV-DLP-STARTUP-GUIDE.md`: Existing concise environment block and canonical link should remain the navigation pattern for other runbooks.

### Established Patterns
- Runtime values originate in an operator PowerShell session, are materialized into `C:\dlp\agent\agent.env`, and are persisted in the `DlpWindowsService` registry `Environment` value for SCM startup.
- Committed documentation uses concrete lab topology but synthetic or redacted sensitive material.
- The endpoint service fails closed with stable configuration errors when required input is missing or invalid.
- `DLP_ROOT_CA_PEM` is interpreted as inline certificate content when it contains `BEGIN CERTIFICATE`; otherwise it is read as a file path.

### Integration Points
- Reconcile documentation against environment reads and defaults in `crates/dlp-windows-service/src/service.rs`.
- Reconcile operator-facing inputs and persistence against `scripts/lab/Invoke-Client01Runtime.ps1`.
- Route first-time setup through `scripts/lab/Initialize-DlpEnvironment.ps1` and final deployment through `Invoke-Client01Runtime.ps1`.
- Preserve links among `ENV-VARS.md`, the startup guide, PKI guide, and lab setup guide without duplicating non-endpoint variable instructions.

</code_context>

- Validation output must report status or redacted metadata, never raw sensitive values.
- Use visibly failing replacement markers rather than realistic-looking fake secrets.
