## Summary

The replan should replace the current “four required variables” emphasis with a setup-first operator journey followed by an equally deep catalog for all 15 variables read by `dlp-windows-service`. The authoritative inventory is six required variables, one conditionally needed enrollment token, and eight variables with service defaults. [VERIFIED: crates/dlp-windows-service/src/service.rs:605-616,633-681]

The most important reconciliation result is that `Invoke-Client01Runtime.ps1` persists only ten variables: the six required service values, optional key ID, conditional enrollment token, poll interval, and health interval. It does not persist `DLP_START_TIMEOUT_SECONDS`, `DLP_STOP_TIMEOUT_SECONDS`, `DLP_PREFERRED_DRIVE_LETTER`, `DLP_SIGN_OUT_GRACE_SECONDS`, or `DLP_DRIVE_HOST_BINARY_PATH`; those five therefore use service defaults in the deployed SCM process even if they existed only in the orchestrator process. [VERIFIED: scripts/lab/Invoke-Client01Runtime.ps1:1129-1150; crates/dlp-windows-service/src/service.rs:605-616,663-680]

**Primary recommendation:** Rewrite `.planning/docs/ENV-VARS.md` around collect → validate → persist → deploy → verify, explicitly publish the 15-variable source inventory and the 10-variable runner persistence boundary, and keep the startup guide as a short link-only navigation surface.

## Authoritative Endpoint Variable Inventory

The source-of-truth values below are quoted verbatim from the service reads so the planner can require a one-to-one documentation audit. [VERIFIED: crates/dlp-windows-service/src/service.rs:605-680]

> Required reads: `"DLP_DEVICE_ID"`, `"DLP_SERVER_URL"`, `"DLP_ROOT_CA_PEM"`, `"DLP_DATA_DIRECTORY"`, `"DLP_CACHE_DIRECTORY"`, `"DLP_CONFIGURATION_PUBLIC_KEY_HEX"`.
>
> Conditional read: `"DLP_AGENT_ENROLLMENT_TOKEN"`.
>
> Defaulted reads: `"DLP_CONFIGURATION_KEY_ID"` = `"phase1-config-signer"`; `"DLP_POLL_INTERVAL_SECONDS"` = `300`; `"DLP_HEALTH_INTERVAL_SECONDS"` = `60`; `"DLP_START_TIMEOUT_SECONDS"` = `60`; `"DLP_STOP_TIMEOUT_SECONDS"` = `10`; `"DLP_PREFERRED_DRIVE_LETTER"` = `'P'`; `"DLP_SIGN_OUT_GRACE_SECONDS"` = `30`; `"DLP_DRIVE_HOST_BINARY_PATH"` = `C:\Program Files\DLP\dlp-drive-host.exe`.

`DLP_ROOT_CA_PEM` is interpreted as inline certificate content only when its value contains `BEGIN CERTIFICATE`; otherwise the service reads it as a filesystem path. [VERIFIED: crates/dlp-windows-service/src/service.rs:638-646]

The duration parser does not reject malformed or zero values: parse failure falls back to the default, while `0` parses successfully. Documentation must describe actual behavior and should not claim the service enforces “positive integer” unless runtime code changes in a different phase. [VERIFIED: crates/dlp-windows-service/src/service.rs:663-670]

The drive-letter parser takes the first character, uppercases it, and does not itself prove that the result is an ASCII letter. Documentation should distinguish a safe operator check from the weaker service parser. [VERIFIED: crates/dlp-windows-service/src/service.rs:605-609]

## Recommended Documentation Architecture

1. Scope and handling taxonomy: cryptographic secret, sensitive identifier, public trust/configuration, ordinary operational setting.
2. End-to-end workflow first: collect → validate → persist → deploy → verify, led by `Initialize-DlpEnvironment.ps1` and completed by `Invoke-Client01Runtime.ps1`.
3. Authoritative inventory/reconciliation table with columns for service behavior, initializer support, runner input, env-file persistence, registry persistence, and effective default.
4. Fifteen equal-depth variable sections: purpose; source/create; representation; redacted validation; persistence/deployment support; errors and fixes.
5. Stable error-to-fix matrix and exposure-response procedure.
6. Manual PowerShell fallback and cross-links to PKI/lab guides, with no duplication of server/provisioning/AD catalogs.

## Validation and Troubleshooting Patterns

- Validate presence with boolean/status output, never `Write-Host $env:NAME` for sensitive values. [VERIFIED: CONTEXT.md D-15]
- Validate the public-key string using length `64` plus a hex-only regex; print only validity and, if useful, a digest/fingerprint rather than the key. The service requires exactly 32 decoded bytes. [VERIFIED: crates/dlp-windows-service/src/service.rs:650-652,684-696]
- Validate root CA forms separately: inline form should be parsed as an X.509 certificate; path form should be absolute/readable and then its content parsed. Do not print certificate bodies during troubleshooting. [VERIFIED: crates/dlp-windows-service/src/service.rs:638-646; CONTEXT.md D-15]
- Validate generated `agent.env` by reporting present variable names and redacted metadata, then compare those names with the registry `Environment` multi-string. The two generated copies must not be hand-edited independently. [VERIFIED: scripts/lab/Invoke-Client01Runtime.ps1:1152-1160,1196-1202; CONTEXT.md D-13]
- `runtime_secrets_missing` is emitted by the runner for the four orchestrator-supplied core values and, outside trusted provisioning, the token. It does not cover the runner-injected data/cache paths. [VERIFIED: scripts/lab/Invoke-Client01Runtime.ps1:211-224]
- `service_config_missing` covers absent required service inputs; `service_config_invalid` covers invalid device ID, unreadable root path, or non-64-hex public key, and can also arise later when TLS client construction rejects configuration. [VERIFIED: crates/dlp-windows-service/src/service.rs:43-57,633-652,112-114]
- Successful documentation-phase verification stops at generated configuration, registry persistence, SCM startup, and redacted health/diagnostics; it must not demand successful enrollment or first configuration polling. [VERIFIED: CONTEXT.md D-17]

## Common Pitfalls

### Treating the initializer catalog as the runtime authority
The initializer spans server, database, AD, provisioning, and endpoint concerns. Use service source for the endpoint inventory and link out for other scopes. [VERIFIED: scripts/lab/Initialize-DlpEnvironment.ps1; CONTEXT.md D-03/D-04]

### Claiming an override persists because it exists in the operator process
Five defaulted service variables are not copied by the runner. The guide must show the effective deployed result and prevent false verification claims. [VERIFIED: scripts/lab/Invoke-Client01Runtime.ps1:1129-1150]

### Printing secrets during validation
Raw environment, env-file, registry, or diagnostic dumps can expose tokens or trust/configuration material. Emit only presence, shape, path accessibility, hashes/fingerprints, and status. If exposure occurs, stop copying, remove artifacts, rotate affected material, and resume with redacted output. [VERIFIED: CONTEXT.md D-15/D-18]

### Overstating validation
The service duration and drive-letter parsers are permissive. Safe docs may impose stricter operator-side checks, but must label them as recommended preflight checks rather than existing service rejection behavior. [VERIFIED: crates/dlp-windows-service/src/service.rs:605-613,663-670]

### Duplicating PKI or provisioning procedures
Cross-link `PEM-KEY-GUIDE.md` and `LAB-SETUP-GUIDE.md`; only explain how their output maps into endpoint variables. [VERIFIED: CONTEXT.md D-03; .planning/docs/PEM-KEY-GUIDE.md; .planning/docs/LAB-SETUP-GUIDE.md]
