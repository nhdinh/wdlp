# Phase 01.2: DLP_AGENT_ENROLLMENT_TOKEN should be obtained automatically when DlpWindowsService installed - Research

**Researched:** 2026-08-13
**Domain:** Windows service deployment automation, PowerShell orchestration, short-lived enrollment token handoff
**Confidence:** HIGH

## Summary

Phase 01.2 removes the manual step in which an operator copies the `DLP_AGENT_ENROLLMENT_TOKEN` output from `Invoke-TrustedProvisioning.ps1` into the orchestrator environment before running `Invoke-Client01Runtime.ps1`. Today the token is minted on LAB-DC01 (the only machine that holds the administrator mTLS provisioning material and has AD access), returned as JSON to the orchestrator on hungdinh-lt, and then persisted into the Windows service registry environment on LAB-CLIENT01 so the service can enroll on first start. The goal is to make `Invoke-Client01Runtime.ps1` obtain that token automatically as part of the service-install flow, without persisting it on hungdinh-lt and without moving administrator provisioning credentials to the endpoint.

The recommended approach is to extend the PowerShell orchestrator so it can invoke the existing trusted-provisioning procedure on LAB-DC01 immediately before installing the service, capture the returned enrollment token in memory, and inject it into the service environment during the same remote session. This preserves the existing security boundary (administrator mTLS material never leaves LAB-DC01), requires no changes to the Rust service or enrollment protocol, and keeps the token short-lived. After the service enrolls once, the device mTLS credential is stored in the DPAPI-protected credential store; the token can then be removed from the service registry environment to avoid leaving a reusable secret on the endpoint.

**Primary recommendation:** Add an `-EnrollmentTokenProvider TrustedProvisioning` mode to `Invoke-Client01Runtime.ps1` that calls the existing trusted-provisioning script on LAB-DC01, captures the token in a constrained variable, and passes it straight into `Install-Client01Service` without writing it to disk on hungdinh-lt.

### Pattern 1: Orchestrator-Mediated Token Handoff

**What:** The orchestrator script on hungdinh-lt calls the trusted-provisioning procedure on LAB-DC01, captures the enrollment token in a constrained PowerShell variable, and passes it into the LAB-CLIENT01 service-install block in the same remote session. The token is never written to disk on hungdinh-lt.

**When to use:** Lab and dev-test topologies where a single trusted orchestrator can reach both the provisioning station and the endpoint. Also suitable for any deployment where the installer can obtain a one-time token from a privileged provisioning API immediately before install.

**Example:**
```powershell
# Source: scripts/lab/Invoke-Dc01Server.ps1:617-652 (existing TrustedProvisioning scenario)
$provResult = Invoke-LabCommand -VMName 'LAB-DC01' -ScriptBlock {
    param($Digest, $Target, $PreferredLetter)
    & C:\dlp\server\scripts\lab\Invoke-TrustedProvisioning.ps1 `
        -ExecutionMachine LAB-DC01 `
        -TargetComputer $Target `
        -PrivilegeManifestDigest $Digest `
        -PreferredDriveLetter $PreferredLetter
} -ArgumentList @($digest, 'LAB-CLIENT01.lab.local', 'P')
$token = ($provResult | ConvertFrom-Json).enrollment_token
# $token is used immediately and never persisted
```

### Pattern 2: Token Cleanup After Enrollment

**What:** After the service has started and the DPAPI credential store contains a usable device credential, remove `DLP_AGENT_ENROLLMENT_TOKEN` from the service registry `Environment` value so the one-time token is not retained on the endpoint.

**When to use:** Always, unless the operator intends to re-enroll the same device repeatedly.

**Example:**
```powershell
# Run after service reaches Running state
Invoke-LabCommand -VMName $ExecutionMachine -ScriptBlock {
    $serviceKey = 'HKLM:\SYSTEM\CurrentControlSet\Services\DlpWindowsService'
    $envLines = Get-ItemPropertyValue -Path $serviceKey -Name 'Environment'
    $envLines = $envLines | Where-Object { $_ -notlike 'DLP_AGENT_ENROLLMENT_TOKEN=*' }
    Set-ItemProperty -Path $serviceKey -Name 'Environment' -Value $envLines -Type MultiString -Force
}
```

### Anti-Patterns to Avoid

- **Do not place administrator provisioning credentials on the endpoint.** The admin mTLS cert/key used for `/api/v1/admin/provisioning` must remain on LAB-DC01. Moving them to LAB-CLIENT01 so the service can self-provision would convert a short-lived token into a long-lived privileged credential on every endpoint.
- **Do not write the enrollment token to disk on hungdinh-lt.** The orchestrator should keep the token in a local variable and pass it directly into the remote service-install block.
- **Do not make the service poll indefinitely for a token.** The service should remain fail-closed (`ReplacementEnrollmentRequired`) when no credential and no token are present, matching the current behavior [VERIFIED: crates/dlp-windows-service/src/service.rs:158-172].
- **Do not bypass the trusted-provisioning fingerprint check.** The device fingerprint digest and AD corroboration must still be computed on LAB-DC01 before the server mints a token.

**Key insight:** The hard problem in this phase is not "get a string from one machine to another" but "do it without violating the trusted-provisioning boundary and without leaving a reusable secret behind." Reusing the existing provisioning route and DPAPI store solves both.

## Common Pitfalls

### Pitfall 1: Token Persists in Service Registry After Enrollment
**What goes wrong:** `DLP_AGENT_ENROLLMENT_TOKEN` remains in the service `Environment` value indefinitely. If an attacker extracts the registry value, they can attempt to enroll a different device or replay the token if it has not expired.
**Why it happens:** The current installer writes the token to the service environment but has no cleanup step after enrollment succeeds.
**How to avoid:** Add a post-enrollment cleanup that removes `DLP_AGENT_ENROLLMENT_TOKEN` from the registry `Environment` once the service has created a usable DPAPI credential. A simple check is to test whether `C:\dlp\agent\data\credentials\device.dpapi` exists and the service is Running.
**Warning signs:** The registry key still contains `DLP_AGENT_ENROLLMENT_TOKEN=*` after the service has been running for more than one poll interval.

### Pitfall 2: Orchestrator Holds Token in a Logged or Serialized Variable
**What goes wrong:** The token is captured in a variable that is later serialized to evidence JSON, written to a transcript, or emitted by `Write-Host` for debugging.
**Why it happens:** PowerShell transcripts and custom evidence objects may accidentally capture the full token if the provisioning result object is passed around unchanged.
**How to avoid:** Extract the token into a dedicated `SecureString` or constrained `[string]` variable immediately, then exclude that variable from all evidence and transcript output. Keep using the existing sanitized provisioning result (digest, drive letter, transport) for evidence.
**Warning signs:** Evidence files or console output contain a JWT-like or opaque alphanumeric string longer than 20 characters.

### Pitfall 3: Trusted Provisioning Fails Silently and Service Installs Without Token
**What goes wrong:** The orchestrator captures an empty or invalid token, does not validate it, and installs the service anyway. The service starts, finds no credential and no token, and enters `ReplacementEnrollmentRequired`.
**Why it happens:** The current `Assert-RuntimeSecretsPresent` check in `Invoke-Client01Runtime.ps1` treats `DLP_AGENT_ENROLLMENT_TOKEN` as required, but a new auto-provisioning path may skip that validation if implemented carelessly.
**How to avoid:** After obtaining the token, assert that it is non-empty and matches the allowed token format (alphanumeric, length <= 512) before writing it to the service environment. If the token is invalid, fail the install before creating or reconfiguring the service.
**Warning signs:** Service installs successfully but `service.log` reports `enrollment_failed` or the service state is not Running.

### Pitfall 4: Re-Enrollment Race When Replacing an Existing Credential
**What goes wrong:** An operator reinstalls the service on a device that already has a valid DPAPI credential, but the installer supplies a fresh token. The service may attempt initial enrollment again depending on how the token presence is evaluated.
**Why it happens:** `ServiceContext::startup` first checks `store.validate_protection()` and only enrolls if no usable credential exists [VERIFIED: crates/dlp-windows-service/src/service.rs:163-166], so the Rust side is safe. However, the installer might overwrite or delete the credential store during binary replacement if not careful.
**How to avoid:** `Install-Client01ServiceBinary` stops the service but must not delete `C:\dlp\agent\data\credentials`. Preserve existing credential and cache directories across reinstalls.
**Warning signs:** A reinstall causes the device to receive a new certificate serial and the old one is unexpectedly revoked.

## Code Examples

### Obtaining and Consuming the Token in One Orchestrator Flow

```powershell
# Source: derived from scripts/lab/Invoke-Dc01Server.ps1:617-652 and
# scripts/lab/Invoke-Client01Runtime.ps1:261-297
function Invoke-TrustedProvisioningFromOrchestrator {
    param(
        [Parameter(Mandatory)][string]$PrivilegeManifestDigest,
        [Parameter(Mandatory)][string]$TargetComputer,
        [Parameter()][char]$PreferredDriveLetter = 'P'
    )
    $resultJson = Invoke-LabCommand -VMName 'LAB-DC01' -ScriptBlock {
        param($Digest, $Target, $PreferredLetter)
        $ErrorActionPreference = 'Stop'
        Set-Location C:\dlp\server
        & scripts/lab/Invoke-TrustedProvisioning.ps1 `
            -ExecutionMachine LAB-DC01 `
            -TargetComputer $Target `
            -PrivilegeManifestDigest $Digest `
            -PreferredDriveLetter $PreferredLetter
    } -ArgumentList @($PrivilegeManifestDigest, $TargetComputer, $PreferredDriveLetter)

    $result = $resultJson | ConvertFrom-Json
    if ([string]::IsNullOrWhiteSpace($result.enrollment_token)) {
        throw 'trusted_provisioning_returned_empty_token'
    }
    return $result.enrollment_token
}

# In the install path:
$token = Invoke-TrustedProvisioningFromOrchestrator `
    -PrivilegeManifestDigest $approvedDigest `
    -TargetComputer 'LAB-CLIENT01.lab.local'
$env:DLP_AGENT_ENROLLMENT_TOKEN = $token
Install-Client01Service -StartAfterInstall
# $env:DLP_AGENT_ENROLLMENT_TOKEN is consumed inside Install-Client01RuntimeSecrets
```

### Removing the Token from Service Environment After Enrollment

```powershell
function Remove-Client01EnrollmentToken {
    Invoke-LabCommand -VMName $ExecutionMachine -ScriptBlock {
        $ErrorActionPreference = 'Stop'
        $serviceName = 'DlpWindowsService'
        $serviceKey = 'HKLM:\SYSTEM\CurrentControlSet\Services\' + $serviceName
        $existing = Get-ItemProperty -Path $serviceKey -Name 'Environment' -ErrorAction SilentlyContinue
        if ($null -eq $existing) { return }
        $cleaned = $existing.Environment | Where-Object { $_ -notlike 'DLP_AGENT_ENROLLMENT_TOKEN=*' }
        Set-ItemProperty -Path $serviceKey -Name 'Environment' -Value $cleaned -Type MultiString -Force
    }
}
```

## Open Questions

1. **Should the token cleanup run automatically after every install, or only on request?**
   - What we know: The service only consumes the token when no credential exists, and the credential is DPAPI-protected after enrollment.
   - What's unclear: Whether operators in the lab need to retain the token for repeated reinstalls or disaster-recovery scenarios.
   - Recommendation: Make cleanup the default, with a `-RetainEnrollmentToken` switch for explicit troubleshooting.

2. **How should the orchestrator authenticate to LAB-DC01 for trusted provisioning?**
   - What we know: `Invoke-Dc01Server.ps1` already requires a VM admin credential and uses PowerShell Direct (`Invoke-Command -VMName`).
   - What's unclear: Whether reusing `Invoke-Dc01Server.ps1 -Scenario TrustedProvisioning` from within `Invoke-Client01Runtime.ps1` is cleaner than calling `Invoke-TrustedProvisioning.ps1` directly.
   - Recommendation: Call `Invoke-TrustedProvisioning.ps1` directly on LAB-DC01 to avoid nesting two orchestrator scripts; document that the VM admin credential must have rights on both LAB-DC01 and LAB-CLIENT01.

3. **What is the desired behavior when a credential already exists?**
   - What we know: The Rust service returns `EnrollmentMode::Existing` and does not use the token if a usable credential is present.
   - What's unclear: Whether the orchestrator should skip trusted provisioning entirely in that case to avoid consuming a one-time token unnecessarily.
   - Recommendation: Check for the existence of `C:\dlp\agent\data\credentials\device.dpapi` on LAB-CLIENT01 before invoking trusted provisioning, and skip token acquisition if a credential is present.
