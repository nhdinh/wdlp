<objective>
Eliminate the manual copy-paste step for `DLP_AGENT_ENROLLMENT_TOKEN` by extending `Invoke-Client01Runtime.ps1` to obtain the token automatically from LAB-DC01 trusted provisioning during service installation, inject it into the service registry environment, and clean it up after the agent enrolls.

Purpose: The current lab flow requires an operator to run `Invoke-Dc01Server.ps1 -Scenario TrustedProvisioning`, copy the returned enrollment token into `$env:DLP_AGENT_ENROLLMENT_TOKEN`, and then run `Invoke-Client01Runtime.ps1`. This manual handoff is error-prone, keeps a short-lived secret in the orchestrator shell environment, and blocks unattended LAB-CLIENT01 runtime verification.

Output: A single PowerShell orchestration script that can deploy and start the endpoint service with an automatically acquired enrollment token, plus updated documentation reflecting the new flow.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| hungdinh-lt -> LAB-DC01 | Orchestrator host invokes trusted provisioning over PowerShell Direct; admin mTLS material stays on LAB-DC01. |
| hungdinh-lt -> LAB-CLIENT01 | Orchestrator host installs service and writes token to service registry Environment over PowerShell Direct. |
| LAB-CLIENT01 service process | SCM creates service with registry Environment; service consumes token once and stores mTLS credential via DPAPI. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01.2-01 | Information disclosure | Token logged in PowerShell transcript, evidence, or console | high | mitigate | Store token in a dedicated constrained variable; exclude it from all evidence and `Write-Host` output; redact before serialization. |
| T-01.2-02 | Tampering | Invalid or oversized token accepted and persisted to service registry | medium | mitigate | Validate token length <= 512 and charset before writing; fail install with `enrollment_token_invalid` if validation fails. |
| T-01.2-03 | Elevation of privilege | Administrator provisioning material copied to LAB-CLIENT01 | critical | mitigate | Keep admin mTLS cert/key on LAB-DC01 only; LAB-CLIENT01 never calls `/api/v1/admin/provisioning`. |
| T-01.2-04 | Denial of service | Credential store deleted during binary reinstall, forcing unnecessary re-enrollment | medium | mitigate | `Install-Client01ServiceBinary` must not delete `C:\dlp\agent\data\credentials`; preserve existing credential and cache directories. |
| T-01.2-05 | Information disclosure | Token remains in service registry after enrollment completes | medium | mitigate | Remove `DLP_AGENT_ENROLLMENT_TOKEN` from registry Environment after `device.dpapi` exists and service is Running, unless `-RetainEnrollmentToken` is set. |
| T-01.2-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages are introduced in this phase; only existing PowerShell orchestration and workspace binaries are used. |
</threat_model>
