# Cross-AI Plan Review — Phase 01.3

## Claude Review

### Summary

The three plans cover the phase decisions well and establish sensible security boundaries: a standalone crate, fail-closed configuration, canonical direct-child path authorization, bounded complete-line reads, peer-derived client identity, redacted HTTP errors, isolated SCM lifecycle, and a manual lab runbook. The reviewer found two concrete blockers in the implementation contract and one significant execution risk: the new Windows service crate needs the same narrow `unsafe_code = "allow"` containment used by the existing service crate; Axum `ConnectInfo<SocketAddr>` must be wired through `into_make_service_with_connect_info`; and the final lab checkpoint depends on VMs already recorded as unreachable.

### Strengths

- Plan 01 cleanly isolates `dlp-log-debug-service` from product crates, matching D-02/D-05 in `01.3-CONTEXT.md:17-21`.
- Malformed or empty-trust configuration falls back to `LocalhostOnly` with no authorized folders.
- Canonicalization plus exact-parent equality prevents string-prefix and link-escape authorization bugs, consistent with `01.3-RESEARCH.md:193-198`.
- The tail reader is byte-bounded and excludes incomplete edge lines.
- Plans include a real TCP tracer test and coverage for link escapes, cap boundaries, CRLF, truncation, and append races.
- Plan 02 derives identity from TCP peer metadata, rejects forwarded identity inputs, uses stable redacted error codes, and preserves SCM isolation from `DlpWindowsService`.
- Plan 03 verifies both application and firewall authorization and records the product service state before and after the debugger exercise.

### Concerns

#### HIGH — Workspace unsafe-code lint conflicts with Windows service macros

The workspace forbids unsafe code at `Cargo.toml:21-22`, while the existing Windows service crate overrides that lint at `crates/dlp-windows-service/Cargo.toml:8-11`. Plans 01 and 02 say to keep the workspace prohibition intact but also require `windows-service` macros. The new crate should explicitly contain the required Windows FFI expansion with a crate-level lint override, or compilation may fail.

#### HIGH — Axum ConnectInfo injection is underspecified

Plan 02 requires `ConnectInfo<SocketAddr>` but does not explicitly require the make-service wrapper. The serving contract should name the mechanism, for example:

`axum::serve(listener, build_router(state).into_make_service_with_connect_info::<SocketAddr>()).with_graceful_shutdown(shutdown)`

Without connect-info injection, the peer extractor will not receive the accepted socket address.

#### HIGH — The blocking lab checkpoint may be unreachable

`.planning/STATE.md:160-162` records LAB-CLIENT01/LAB-DC01 runtime scenarios as blocked by VM unreachability. Plan 03 requires an administrator session on LAB-CLIENT01 and probes from LAB-DC01 and LAB-DC02 but does not define a blocked-verification handoff or partial acceptance path.

#### MEDIUM — Wave 1 binary and platform boundaries need precision

Plan 01 creates `src/main.rs` before Plan 02 adds the SCM adapter. It should explicitly define Wave 1's main as a non-Windows-safe stub or thin dispatcher and require `#[cfg(windows)]`, following `crates/dlp-windows-service/src/main.rs:25-58`.

#### MEDIUM — Listener ownership and bind behavior need executable assertions

The HTTP serving abstraction should accept a pre-bound `TcpListener`: production binds `0.0.0.0:<port>`, tests bind `127.0.0.1:0`, and SCM reports `Running` only after the listener is owned successfully.

#### MEDIUM — Windows-only test filters can silently exercise nothing

`cargo test --locked -p dlp-log-debug-service service_` may match no tests on non-Windows hosts when SCM tests are gated. Add a portable test for the HTTP error/status mapping or another cross-platform service contract.

#### MEDIUM — Runbook commands need automated syntax validation

The planned `icacls`, `New-NetFirewallRule`, `sc.exe`, and percent-encoded request commands do not exist yet and cannot currently be checked. Add a PowerShell parser check before the human checkpoint, and clearly label the temporary firewall widening window.

### Suggestions

1. Mirror `crates/dlp-windows-service/Cargo.toml:8-11` with a documented narrow unsafe-code override in the new Windows service crate.
2. Put the exact `into_make_service_with_connect_info::<SocketAddr>()` serving contract in Plan 02 actions and acceptance criteria.
3. Define `serve_http` around a pre-bound listener and verify socket ownership before SCM `Running` status.
4. Specify `#[cfg(windows)]` boundaries and a portable Wave 1 `main.rs` behavior.
5. Add a non-Windows test that always exercises the stable HTTP error/status map.
6. Add a lab-unavailability outcome that records the checkpoint as blocked with evidence, while preserving the remaining manual verification for later completion.
7. Syntax-parse the generated PowerShell runbook or a versioned `tests/windows/` verification script before asking a human to execute it.
8. Handle the baseline case where `DlpWindowsService` is not installed so the isolation comparison cannot report a false change.

### Risk Assessment

**Overall: MEDIUM.** Goal coverage, security boundaries, and dependency isolation are good. The unsafe lint and missing ConnectInfo wiring are implementation blockers but straightforward to correct in the plans. The largest schedule risk is Plan 03's dependence on currently unreachable lab infrastructure.
