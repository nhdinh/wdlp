# Phase 01.2: dlp-agent-enrollment-token-should-be-obtained-automatically - Context

**Gathered:** 2026-08-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Make `Invoke-Client01Runtime.ps1` obtain the short-lived enrollment token through trusted provisioning, pass it safely to `DlpWindowsService`, and clean it up after enrollment. This phase does not change the Rust service or provisioning protocol.

</domain>

<decisions>
## Implementation Decisions

### Failure recovery and token lifecycle
- **D-01:** If provisioning succeeds but installation or startup fails, clean the token and require a fresh provisioning attempt on retry.
- **D-02:** Cleanup failure is a hard failure; identify both `agent.env` and registry `Environment` locations needing remediation.
- **D-03:** Leave partially installed services and binaries intact for diagnosis; remove only token state.
- **D-04:** Every retry requests a fresh trusted-provisioning token; do not reuse an existing token.

### Existing-credential behavior
- **D-05:** If `device.dpapi` already exists, skip normal trusted provisioning and continue with the existing credential.
- **D-06:** Add explicit `-ForceReenrollment` support for credential replacement; it is not part of the normal path.
- **D-07:** `-ForceReenrollment` may mutate only when combined with `-Apply`; preview mode remains non-destructive.
- **D-08:** Forced re-enrollment preserves service installation and data/cache directories, replacing only enrollment credentials and related token state.

### Operator-facing diagnostics
- **D-09:** Normal output reports only high-level success/failure and final service state.
- **D-10:** Errors include a stable error code and concise operator-safe remediation hint.
- **D-11:** Detailed diagnostics are available only through an explicit opt-in switch and remain redacted.
- **D-12:** Always redact enrollment tokens, private keys, passwords, full certificate contents, and raw credential blobs. Names, lengths, paths, fingerprints, and status may be shown.

### the agent's Discretion
- Exact switch name for the opt-in diagnostic mode, provided it is explicit and redaction is mandatory.
- Exact stable error-code wording where existing project conventions do not already define one.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `Invoke-Client01Runtime.ps1` already exposes `-EnrollmentTokenProvider`, `-RetainEnrollmentToken`, token validation, credential detection, and cleanup helpers.
- Existing `-Apply` preview/apply boundary can protect force-reenrollment mutations.

### Established Patterns
- Trusted provisioning runs on `LAB-DC01`; administrator mTLS material must not move to `LAB-CLIENT01`.
- Generated `agent.env` and registry `Environment` are managed copies and must be updated together.
- DPAPI credential presence is the durable enrollment success signal.

### Integration Points
- Token acquisition feeds service installation on `LAB-CLIENT01`.
- Cleanup runs after service state and credential establishment checks.
- Documentation and static PowerShell gates must reflect the selected failure, credential, and redaction behavior.

</code_context>

<specifics>
## Specific Ideas

- Fresh retries should never depend on a token left by an earlier failed attempt.
- Force re-enrollment is an operator-directed exception, not an automatic recovery behavior.
- Normal output should be intentionally sparse; diagnostic detail is opt-in and safe to share.

</specifics>
