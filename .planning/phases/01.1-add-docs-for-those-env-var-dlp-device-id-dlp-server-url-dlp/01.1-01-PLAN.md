  <name>Create ENV-VARS.md reference document</name>
  <files>.planning/docs/ENV-VARS.md</files>
  <action>
    Create `.planning/docs/ENV-VARS.md` as the canonical operator reference for DLP Windows service runtime environment variables.
    
    Content must include:
    - A short intro explaining that these variables are runtime-only secrets and configuration, never committed to source control, and sourced from the operator's secret provider in production/lab.
    - A table or section listing every variable consumed by `crates/dlp-windows-service/src/service.rs:403-447`:
      - Required: DLP_DEVICE_ID, DLP_SERVER_URL, DLP_ROOT_CA_PEM, DLP_DATA_DIRECTORY, DLP_CACHE_DIRECTORY, DLP_CONFIGURATION_PUBLIC_KEY_HEX.
      - Optional: DLP_CONFIGURATION_KEY_ID, DLP_AGENT_ENROLLMENT_TOKEN, DLP_POLL_INTERVAL_SECONDS, DLP_HEALTH_INTERVAL_SECONDS, DLP_START_TIMEOUT_SECONDS, DLP_STOP_TIMEOUT_SECONDS.
    - For each variable: purpose, format/validation rules, example value, whether required, and default if optional.
    - A dedicated "Collecting or creating the four required variables" section with step-by-step instructions for:
      - DLP_DEVICE_ID: how to choose/parse a valid device identifier (refer to `DeviceId::parse` expectations; use a stable, hostname-derived or assigned identifier; avoid spaces/special characters).
      - DLP_SERVER_URL: management server base URL format, example `https://LAB-DC01:8443`, and how to determine host/port from the deployed server.
      - DLP_ROOT_CA_PEM: how to obtain the pinned root CA PEM (from the CA that issued the server certificate or the lab trusted-provisioning output), the requirement that it is the public root only, and that the service currently expects either the PEM content as a multi-line string or a filesystem path.
      - DLP_CONFIGURATION_PUBLIC_KEY_HEX: how to obtain the 32-byte Ed25519 public key used for signed configuration bundle verification, formatted as exactly 64 lowercase hex characters, and where it originates in the lab (configuration signer key output from server/trusted provisioning).
    - A "Runtime-only vs committed defaults" section explaining which values can live in example configs (host names, key IDs, intervals) and which must always come from a secret provider (certificates, keys, tokens, device identity).
    - A PowerShell snippet template that sets all required variables locally, with placeholders for secret values, suitable for pasting into a lab setup session.
    - A final paragraph pointing to `scripts/lab/Invoke-Client01Runtime.ps1` as the lab deployment script that consumes these variables and persists them into the service environment.
    
    Do not include any actual secrets or real certificate/key values. Keep examples synthetic but realistic.
  </action>
